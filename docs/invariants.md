# Invariants

The properties the system proves: LED for the ledger, TEN for tenancy, SRV for serving, RUN for runs, whose rows land with what they cover. A behavior shows one example; an invariant holds for every input. The **S** properties are proven by the crash test below, and by a seeded fault simulator in a later release.

**Form:** **T** a type or API makes the violation unrepresentable · **U** a unit or integration test · **S** a property checked under faults · **B** a behavior scenario · **C** a CI check, which must reject a violating fixture.

## Crash test

A parent process drives a child process that owns an engine's root, its requests over a socket and the answers over a pipe, with keyed and unkeyed emits and mixed batches, each a call with a key. The child opens its engine with a seed the parent chose, except in the rows below that say otherwise, so the parent always knows an admin key; it makes a second key, with which it emits in turn, and after `ready` prints the environment reference and that key's ID. The parent verifies through an engine it opens on that root after the kill, without a seed unless a row says otherwise. Secrets never pass over stdout, stderr or an argument: the child's stdin is one end of a socket pair, over which it reads its seed, and over which, as an open or `create_key` comes to store a key and before any point that storing reaches, it tells the parent the environment, the key's ID and, unless the key is a seed, its secret; a finishing open without a seed tells its replacement whether or not there is a key to replace, and an admitted `create_key` its key whether or not it is then refused. So the parent proves that exact key accepted or refused after the reopen. The child is built with the `__fault-points` cargo feature, a hidden, unstable opt-in on `ironflowx-cell`, `ironflowx-store` and `ironflowx-operations` with no API promise; enabling it can make a durable commit answer `Unknown`. The hooks themselves, one for points and one for keys, live in `ironflowx-core`, and each crate's `__fault-points` forwards to core's; without the feature no hook is compiled. `ci/no-fault-points.sh` checks that no published crate enables it, by default or in its dependency tree, and that a published crate turns on a dependency's `__fault-points` only from its own feature of that name (`ci/fixtures/fault-points-forwarded` must pass, `ci/fixtures/fault-points` must fail), so the crash-test crate enabling it, and the engine's tests through a dev-dependency, do not leak into a published build; the parent reads `<root>/ledgers/<environment-id>/read.db` directly, read-only, to see sequences and the applied position.

- **Named fault points**, each run deterministically, the child and parent meeting at a barrier: before the append, after fsync and before the acknowledgment, after the acknowledgment and before the fold, mid-fold, during open, and the points inside an open and around a key change, below. At a point before the acknowledgment the parent then sends a `probe`; the child polls the stopped request before answering `pending`, so a reply already sent shows, by the same barrier and not by a timed wait. **Seeded random kills**, a separate test, try cases nobody named; the seed is printed and replays the run.
- **The parent records** each acknowledged event ID and key, the cursor of its last list, and each request with no answer. Every new event carries a unique marker in its metadata, so the parent can find it without its ID; it also knows each item's expected outcome.
- **After each kill of a working ledger** it reopens the engine twice and asserts:
  - no reopen mints a key, reports a lost secret or applies a seed, and the seed still authenticates and reaches the environment the child reported, its incarnation token included;
  - every event's `emitted_by` is the key that emitted it;
  - every acknowledged ID reads back, and every acknowledged key returns its original ID;
  - the new events of an unanswered request are all present or all absent; its duplicates and refusals store nothing;
  - event sequences have no gap and no repeat, and event times never decrease while the seed steps the `ManualClock` both ways;
  - both reopens give the same events, keys, sequences and applied position;
  - the recorded cursor still pages from the same place.

**Kills inside an open.** The child opens a fresh root, or one an earlier kill or open left, and is killed at the point. A bootstrapping open reaches its undo by an obstruction the child puts in its ledger's way: in staging, the read store's place taken; after the rename, the ledger's lock held. In "before the mark", every point is run: after the bootstrap commits, before and after the staged ledger's genesis record, before and after the rename, and before the mark commits.

| Killed | After reopen |
|---|---|
| Bootstrapping with seed A: before the schema's transaction commits, or the bootstrap's | No bootstrap and no ledger exist; the next open bootstraps |
| Bootstrapping with seed A: after the bootstrap commits, while the ledger is staged | A finishing open deletes staging, builds the ledger again and marks it; A authenticates and emits |
| Bootstrapping with seed A: after the rename, before the mark | A finishing open opens that ledger and marks it; A authenticates; `lost_secret` is false |
| A bootstrapping open that failed in staging, with seed A and without a seed: before its undo deletes staging, after it and before the rows' deletion commits, or after that | Before the commit, an unmarked bootstrap, which a finishing open completes; after it no bootstrap and no ledger exist, and the next open bootstraps. Never `Orphaned` |
| A bootstrapping open that failed after its rename, with seed A and without a seed: before its undo, or after it, which undoes nothing | An unmarked bootstrap and its ledger, which a finishing open completes. Never `Orphaned` |
| Bootstrapping without a seed: before the mark | The finishing open revokes the key the parent was told of, which no longer authenticates, reports `lost_secret` and returns a replacement, which authenticates as admin |
| Bootstrapping without a seed: after the mark, before `open` returns | The reopen returns no secret and `lost_secret` false; the key stays listed; `recover_admin_key` returns a key that authenticates as admin |
| Bootstrapping with seed A: after the mark, before `open` returns | The reopen returns nothing new; A authenticates |
| Bootstrapping with seed A: before the mark; the reopen passes seed B | The finishing open marks, then rotates to B: B authenticates, A does not, `seed` is `Current` |
| Bootstrapping without a seed: before the mark; the reopen passes seed B | The finishing open marks, revokes the key the parent was told of, reports `lost_secret`, returns no replacement and applies B: only B authenticates, `seed` is `Current` |
| A finishing open of a bootstrap with seed A or without one, itself without a seed or with B: at every point it reaches, its seed's included | Before the mark commits, the bootstrap is as it was; after it, marked, the minted key revoked, the replacement or B stored only if its transaction committed |
| A later open that rotates A to B: before and after `apply_seed` commits | Exactly one of A and B authenticates: A unless `apply_seed` committed |

After each kill the parent compares, on a copy, so that the next open recovers the WAL itself, the bootstrap state, how many rows each table holds, and each key's ID, origin, digest and whether it is revoked; and what `ledgers/` and the staged ledger hold, that a ledger left in staging is never used and one in place never replaced. Once no kill follows, it opens the root twice or more. After each open it compares all that again, and checks what the open returned, that every key it was ever told of, stored or not, is accepted as an admin key or refused as it should be, and that every event it emitted so far, with each key that works, is listed once, in order, with the key that emitted it.

**Kills around a key change.** The child has opened and works; the seed creates and revokes keys and each key is used while the clock steps both ways, every answer checked. Then the parent arms a point, or none, sends one more request and kills the child there, its answer still pending, or with the answer in hand.

| Killed | After reopen |
|---|---|
| `create_key`: before its commit, after it, or once answered | The very key the parent was told of is listed, and works, only if the commit landed |
| `revoke_key`: before its commit, after it, or once answered | An unrevoked key is refused only if the commit landed; it stays listed |
| A refusal as expired, by admission or inside the transaction of the key's own `create_key`, whose re-check `revoke_key` shares: before the expiry's commit, after it, or once answered | With the clock stepped back, the key stays refused only if the commit landed, as it has once the refusal is answered; a key with the same expiry that was not refused works |
| A refusal as expired whose recording fails at its commit, at a constraint checked there: once answered | It is refused alike, and the point after the commit is not reached; with the clock stepped back, the key works |

After each kill, and each open after it, the parent compares, on a copy, each stored key's ID, digest, recorded expiry and revoke. It opens twice with the clock stepped back before every expiry, and each time checks every field of every listed key, and that each key it was ever told of, stored or not, is accepted with its scopes or refused as every invalid key is.

Built under [#6](https://github.com/ironflowx/foundation/issues/6), in the unpublished `ironflowx-crash-test` crate (D23), in `crates/ironflowx-crash-test/tests/crash.rs`, the kills inside an open in `tests/crash/opens.rs` and those around a key change in `tests/crash/keys.rs`: the full workload (keyed and unkeyed emits, a duplicate and a refused emit, mixed batches with new items, stored and in-batch duplicates and refusals, a list, and `ManualClock` steps both ways), killed at every named fault point of a working ledger, each on a single emit and on a mixed batch: **before the append**, **after fsync and before the acknowledgment**, **after the acknowledgment and before the fold**, **mid-fold** (inside the read store's transaction for the record, its rows written and the applied position not yet moved), and **during open** (the child first stopped after the acknowledgment, then the reopen killed inside recovery's fold of that record, at the same place as mid-fold). After each, until reopen, the read store holds nothing of the stopped request, its rows and applied position moving together; the request's new events are all absent (before the append) or all present (from after fsync on); every check above holds; and a test shows a broken expectation fails naming its request. Then `seeded_random_kills` runs `CRASH_KILLS` seeded kills, 100 by default: its seed picks a kill of one of the three kinds. Around a key change, it picks up to ten requests, then a create, a revoke or a refusal as expired, the latter of a key made for it, and where it is killed, then opens at a time it picks, before or after the keys' expiries, and twice with the clock stepped back, every check above made each time. Inside opens, it picks up to three opens, each with one of three seeds or without and killed at any point it then reaches or left to finish, then opens without a seed, with one or without, and after a recovery, every check above made after each. The tests run one at a time, since a spawned child shares the parent's lock files until it execs. In a working ledger, it picks a workload of emits, batches and lists over a few keys with `ManualClock` steps both ways between them, one of that ledger's five points, and which append to stop on (during open, the append to stop after the acknowledgment on before killing the reopen); after the checks above it opens the engine once more with the clock behind the last event and checks a new event takes that event's time. Every event's time is checked exactly against the clock the parent stepped. Kill `i` takes seed `CRASH_SEED + i`, the first random unless set; the run prints its first seed up front, so a hung run can be replayed, and a failing kill prints `CRASH_SEED=<seed> CRASH_KILLS=1`, which replays it. A new fault point fails to build until the match beside the seeded kills' list names it, as a working ledger's, an open's or a key change's; the points inside opens are listed in `tests/crash/opens.rs`, and those around key changes in `tests/crash/keys.rs`. CI's `test` job runs it on every PR, on Linux and on macOS: every named fault point and 100 seeded kills (`CRASH_KILLS=100`, a fresh first seed each run); `ci/check.sh` runs the same. There is no longer scheduled run; before publishing, a longer soak is started by hand: CI's `soak` job, 10000 seeded kills by default on Linux and macOS (`ci/README.md`).

A kill keeps the operating system's page cache, so this test proves crash durability, not power-loss durability. The simulator proves the second in a later release.

### Server crash test

The server crash test kills the real `ironflowx` binary under load and around key publication and recovery, then checks what survives. It is [`ironflowx/ironflow`](https://github.com/ironflowx/ironflow)'s, with the binary; foundation's `conformance` job runs it against each foundation PR that is not only `docs/` and Markdown, at the app branch `ci/app-ref` names (D85, D122).
