# Invariants

The properties the system proves: LED for the ledger, TEN for tenancy. A behavior shows one example; an invariant holds for every input. The **S** properties are proven by the crash test below, and by a seeded fault simulator in a later release.

**Form:** **T** a type or API makes the violation unrepresentable · **U** a unit or integration test · **S** a property checked under faults · **B** a behavior scenario · **C** a CI check, which must reject a violating fixture.

## Crash test

A parent process drives a child process that owns an engine's root, over a pipe, with keyed and unkeyed emits and mixed batches, each a call with a key. The child opens its engine on a fresh root without a seed and, after `ready`, prints the environment reference and the minted bootstrap key; the parent verifies through an engine it opens on that root after the kill, with that key. The child is built with the `__fault-points` cargo feature, a hidden, unstable opt-in on `ironflowx-cell` with no API promise; enabling it can make a durable commit answer `Unknown`. The hook itself lives in `ironflowx-core`, and `ironflowx-cell`'s `__fault-points` forwards to core's; without the feature no hook is compiled. `ci/no-fault-points.sh` checks that no published crate enables it, by default or in its dependency tree, and that a published crate turns on a dependency's `__fault-points` only from its own feature of that name (`ci/fixtures/fault-points-forwarded` must pass, `ci/fixtures/fault-points` must fail), so the crash-test crate enabling it, and the engine's tests through a dev-dependency, do not leak into a published build; the parent reads `<root>/ledgers/<environment-id>/read.db` directly, read-only, to see sequences and the applied position.

- **Named fault points**, each run deterministically, the child and parent meeting at a barrier: before the append, after fsync and before the acknowledgment, after the acknowledgment and before the fold, mid-fold, and during open. At a point before the acknowledgment the parent then sends a `probe`; the child polls the stopped request before answering `pending`, so a reply already sent shows, by the same barrier and not by a timed wait. **Seeded random kills**, a separate test the test runner may run alongside the named ones, try cases nobody named; the seed is printed and replays the run.
- **The parent records** each acknowledged event ID and key, the cursor of its last list, and each request with no answer. Every new event carries a unique marker in its metadata, so the parent can find it without its ID; it also knows each item's expected outcome.
- **After each kill** it reopens the engine twice and asserts:
  - no reopen mints a key, and the child's key still authenticates and reaches the environment the child reported, its incarnation token included;
  - every acknowledged ID reads back, and every acknowledged key returns its original ID;
  - the new events of an unanswered request are all present or all absent; its duplicates and refusals store nothing;
  - event sequences have no gap and no repeat, and event times never decrease while the seed steps the `ManualClock` both ways;
  - both reopens give the same events, keys, sequences and applied position;
  - the recorded cursor still pages from the same place.

Built under [#6](https://github.com/ironflowx/foundation/issues/6), in the unpublished `ironflowx-crash-test` crate (D23), in `crates/ironflowx-crash-test/tests/crash.rs`: the full workload (keyed and unkeyed emits, a duplicate and a refused emit, mixed batches with new items, stored and in-batch duplicates and refusals, a list, and `ManualClock` steps both ways), killed at every named fault point, each on a single emit and on a mixed batch: **before the append**, **after fsync and before the acknowledgment**, **after the acknowledgment and before the fold**, **mid-fold** (inside the read store's transaction for the record, its rows written and the applied position not yet moved), and **during open** (the child first stopped after the acknowledgment, then the reopen killed inside recovery's fold of that record, at the same place as mid-fold). After each, until reopen, the read store holds nothing of the stopped request, its rows and applied position moving together; the request's new events are all absent (before the append) or all present (from after fsync on); every check above holds; and a test shows a broken expectation fails naming its request. Then `seeded_random_kills` runs `CRASH_KILLS` seeded kills, 100 by default: from its seed, each picks a workload of emits, batches and lists over a few keys with `ManualClock` steps both ways between them, one of the five points, and which append to stop on (during open, the append to stop after the acknowledgment on before killing the reopen); after the checks above it opens the engine once more with the clock behind the last event and checks a new event takes that event's time. Every event's time is checked exactly against the clock the parent stepped. Kill `i` takes seed `CRASH_SEED + i`, the first random unless set; the run prints its first seed up front, so a hung run can be replayed, and a failing kill prints `CRASH_SEED=<seed> CRASH_KILLS=1`, which replays it. A new fault point fails to build until it is named beside the list the seeded kills pick from. CI's `test` job runs it on every PR, on Linux and on macOS: every named fault point and 100 seeded kills (`CRASH_KILLS=100`, a fresh first seed each run); `ci/check.sh` runs the same. There is no longer scheduled run; before publishing, a longer soak is started by hand: CI's `soak` job, 10000 seeded kills by default on Linux and macOS (`ci/README.md`).

A kill keeps the operating system's page cache, so this test proves crash durability, not power-loss durability. The simulator proves the second in a later release.
