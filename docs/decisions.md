# Decisions

Every architecture decision, numbered across all milestones. Numbers are never reused. A decision a later one overturns stays, marked "Superseded by Dnn" in its Why cell.

From 0.2 on, a milestone's PRD issue assigns its decision numbers up front and each lands with the PR that builds it, so the table can skip numbers still to land: 0.2's are D27–D46 ([#64](https://github.com/ironflowx/foundation/issues/64), which renumbered its D25 and D26, taken on `main` first, as D45 and D46), and D47, made as 0.2 closed ([#101](https://github.com/ironflowx/foundation/issues/101)).

**Since** is the milestone that made the decision. From D23 on, the issue or PR that made it is in that row's git history. D1–D22 moved here from the [0.1 architecture doc](https://github.com/ironflowx/foundation/blob/93f0bb261276d7522180d7307464256239a44030/docs/milestones/0.1-ledger/architecture.md#decisions); their history is in that file's log.

| # | Since | Decision | Why |
|---|---|---|---|
| D1 | 0.1 | `Operations` in 0.1 is `emit`, `emit_batch`, `get_event`, `list_events`, as hand-written Rust types. Data and metadata are bytes that must hold JSON (D22); optional fields are `Option` | Event rules own every data and range check, for every door: duplicate keys, lone surrogates and invalid UTF-8 exist only in the bytes as sent |
| D2 | 0.1 | Every `Operations` call takes a `Call`, opaque and empty in 0.1 | The trait does not change shape when 0.2 adds the credential |
| D3 | 0.1 | Read your writes through a committed head published before the acknowledgment ([Commit and read](architecture.md#commit-and-read)) | One fsync on the acknowledgment path, and read your writes holds across clients |
| D4 | 0.1 | The append is the segment log's blocking call, made on the writer's own thread | The writer is the log's only writer, so it knows when a commit lands |
| D5 | 0.1 | Every check, including the version range, runs before the idempotency lookup | The same request is refused the same way, first time or repeat |
| D6 | 0.1 | Events list newest first by event sequence | Commit order is total, so two events never tie |
| D7 | 0.1 | The event clock never goes back: each record's time is the later of the clock and the last committed time | Restarts and clock steps keep event time ordered |
| D8 | 0.1 | A ledger refuses a directory whose format version, environment ID or incarnation token differs | Formats change freely before 1.0; a loud refusal beats a silent misread |
| D9 | 0.1 | A batch is one record: items are checked one by one, new items commit together, and the answer has one result per input in order | Partial validation, atomic commit |
| D10 | 0.1 | The writer mints event IDs (UUIDv7) and `decide` draws them only for new events | Event rules stay pure; an ID exists before the record is written |
| D11 | 0.1 | An unknown append outcome closes the ledger until reopen; there is no append retry | After reopen the log says whether the record landed |
| D12 | 0.1 | Event rules parse the bytes with `serde_json` (`from_slice`, which refuses invalid UTF-8 in the same pass) and a visitor that deserializes every key and string (never `IgnoredAny`), erroring on a repeated key, a NUL or a number out of range. `serde_json` hands keys over unescaped and refuses unpaired surrogate escapes, but only for values it decodes. With `serde_json`'s `arbitrary_precision` on, a number that is not a 64-bit integer arrives as a one-entry map under `$serde_json::private::Number`, so an object whose first key is that string is read as a number | No second JSON parser. The key is internal to `serde_json`; no client is known to need it first in an object |
| D13 | 0.1 | Environment and event IDs are UUIDv7 | One opaque ID format for every resource |
| D14 | 0.1 | The genesis record, not `read.db`, holds the directory's identity | A swapped or rebuilt read store cannot pass for another environment |
| D15 | 0.1 | The writer is one serial thread: decide, append, fsync, publish, acknowledge, fold, then the next submission. 0.1 sets no performance target | `decide` reads the read store, with no overlay of unfolded records to keep right |
| D16 | 0.1 | `segment-log-core` comes from crates.io at an exact version, pinned only in `crates/ironflowx-cell/Cargo.toml`; tag-pinned links to its docs match it (`ci/doc-pins.sh`) | A published crate cannot depend on a git revision |
| D17 | 0.1 | A lint, not the type system, keeps `SequencedTime`'s constructor inside `ironflowx-cell`. One helper in `crates/ironflowx-events/tests/rules.rs` is exempt, by an `#[expect]` on that function alone: it stands in for the ledger to call `decide` | The type is in core so that pure event rules can take one, and Rust cannot open a constructor to one downstream crate only |
| D18 | 0.1 | `Timestamp` has one integer encoding, `i64` milliseconds. The SQLite impl is in `ironflowx-cell` on a private wrapper, and the record in the log uses the same pair | Core stays free of `rusqlite` (LED-15), and the log stores event time too |
| D19 | 0.1 | `open` does not refuse a sealed log | The library reports a seal only on append. A refusal at open waits for it to expose one |
| D20 | 0.1 | The behaviors run under the `cucumber` crate, in an unpublished workspace crate | The feature files are the spec, run from [`behaviors/`](behaviors/) |
| D21 | 0.1 | The public-API checks compare `cargo-public-api` output with a committed snapshot, on a pinned nightly toolchain in one CI job | The tool needs rustdoc JSON, which stable does not emit. Every other job stays on the pinned stable |
| D22 | 0.1 | Event data and metadata are bytes by type and JSON by rule: `Vec<u8>` in `Operations` and event rules, which still require one JSON value for data and one JSON object for metadata under every rule in the [event-rules table](architecture.md#event-rules), and refuse invalid UTF-8. When a non-JSON payload is needed, the event gains an optional first-class content type: absent means JSON, non-JSON data is stored and returned as sent, and every feature that reads inside data skips it. 0.1 builds nothing for the content type | The engine reads inside data (`$redacted` now; filters, keys, schemas and redaction later), so data cannot be opaque. JSON-only can gain a content type later without touching a stored event; the reverse cannot be undone. Bytes by type puts the UTF-8 check in event rules, for every door |
| D23 | 0.1 | The crash test lives in an unpublished workspace crate: a child binary that owns an engine's root and a parent test that drives it over stdin and stdout. The child opens with a seed the parent chose, except where the test is of an open without one, and after `ready` prints the environment reference; the parent verifies through an engine of its own. Its stdin is one end of a socket pair: the seed goes in over it, and before any point that storing a key reaches, an open's or `create_key`'s, the child tells the parent over it the environment, the key's ID and, unless the key is a seed, its secret, so no secret passes over stdout, stderr or an argument. Two process-wide hooks, one for points and one for those keys, and `FaultPoint` live in `ironflowx-core` behind its `__fault-points`; a crate that reaches a point (today `ironflowx-cell`, `ironflowx-store` and `ironflowx-operations`) forwards its own `__fault-points` to core's and calls the hook at each named fault point, on the thread that reaches it. A published crate may turn on a dependency's `__fault-points` only from its own feature of that name, never by default or from another feature; a dev-dependency, which does not ship, may turn it on for a crate's own tests. The child's hook prints `at <point>` on its chosen pass, or on the first pass once a request arms the point, and parks that thread; the parent kills it with SIGKILL on reading the line | The kill lands exactly at the point, by a barrier, not by timing. A process-wide hook reaches points that have no `Ledger` yet, such as during open. In core, any crate can reach a point; forwarding the one feature keeps the hook out of every build that does not ask for it by name. A later fault point adds a name and reuses the hook and the `at <point>` line; at a point before `ready` (inside an open) the parent waits for that line instead of `ready`. Told the key before the kill, the parent proves that key, not some other, accepted or refused after it; on a channel of its own, the secret reaches no log |
| D24 | 0.1 | The writer admits up to 16 waiting submissions. Additional callers await a queue slot | Caps queued work retained after callers cancel while a commit or fold is in progress |
| D25 | 0.1 | The ledger holds its own lock file, `<dir>/ledger.lock`, from before it opens the log until close | The segment log releases its own lock when it is sealed, so without one a second opener could rebuild the read store under a running ledger |
| D26 | 0.1 | Published crates take dependencies as caret ranges. Two are exact: `segment-log-core` (D16) and `serde_json`, whose internal recursion limit the 127-depth rule relies on; those two keep the cost, so an embedder must resolve to the same versions. `Cargo.lock` holds CI to exact versions, so a later version is first built in a `cargo update` PR, and a lower bound rises when code starts using a newer API | An exact pin in a library conflicts with any embedder graph that needs another patch of that crate. Caret ranges on 0.x crates still stay within one minor version |
| D27 | 0.2 | Scopes are a set of `read`, `write`, `admin`, none implying another; a key asked for with no scopes gets `{read}`; `whoami` needs none | Least privilege for agents; a set still works when later releases add scopes |
| D28 | 0.2 | A new key holds no scope its creator lacks and has no expiry later than its creator's | No key grants more than it holds, in scope or in lifetime, by the clock |
| D29 | 0.2 | A key is bound to one environment and incarnation, stored on its row; no call selects one; `lookup_key` and `verify` both check the engine's `EnvRef` | Nothing to forge, nothing to resolve, and a key of an earlier incarnation is refused twice over |
| D30 | 0.2 | Unknown, wrong-secret, revoked, expired and foreign keys get one answer: `Unauthenticated` "invalid API key", no hint | No refusal tells which keys exist or once existed |
| D31 | 0.2 | A missing scope is `PermissionDenied` and names the scope in `hint` | An agent can ask for the right key without trial and error |
| D32 | 0.2 | `Engine::open` parses the seed, checks for a bare ledger, then locks the root, before any other read or write; defaults are named `default` with random IDs per install | A losing opener changes nothing; a refused directory keeps its data; fixed IDs would collide when a project moves between installs |
| D33 | 0.2 | A seed is applied only on finishing and later opens, after the ledger opens; a new key ID rotates the current seed; a revoked seed opens and stays revoked; another digest or origin under a used key ID is refused, and a finishing open checks that before its mark | Repeatable deployments without a secret on disk; a failed open never rotates; a revoked key never returns, and a host that revoked its seed still starts; a refused open never writes `control.db` |
| D34 | 0.2 | `recover_admin_key` is a host-only function, not an operation, refused until the bootstrap is marked; revoking the last admin key is allowed | A lost secret or a revoked last key is recoverable by whoever holds the data directory, and an undo can never delete a recovered key |
| D35 | 0.2 | Revoking sets `revoked_at`; the row stays; a created key records its creator; `list_keys` pages newest first by `seq` | Every `key:` emitter names a row, a compromised key's offspring can be found and revoked, kept rows never make one unbounded answer, and `seq` gives a total order a millisecond clock cannot |
| D36 | 0.2 | A submission is attributed by a `SubmitAs`, passed beside it: `Ledger::submit(Submission, SubmitAs)`, so `Submission` and `decide` do not change. A read returns an `Emitter`, which nothing converts into a `SubmitAs`. `SubmitAs::key` is confined to the credentials crate by a lint, as D17 (clippy outside `ironflowx-core`, `ci/no-key-attribution.sh` inside it), and `Grant::submit_as`, its one caller, to the engine by clippy; `SubmitAs::embedder` is open to any caller. A direct ledger caller is trusted. The engine is the only `Operations` in process and attributes each submission to the calling key, from its grant; the ledger has no `Operations` of its own (0.1's adapter over a bare ledger is removed) | Credentials sit above the ledger, so the ledger trusts its caller; a read value that cannot be resubmitted keeps one caller from replaying another's attribution; `Operations` always means credentialed |
| D37 | 0.2 | `required_scope` is an exhaustive match beside the `Operations` trait; `admit` takes the required scope, not the operation | One table for the engine and `describe`; a new operation without a scope does not compile; credentials stay free of `proto` |
| D38 | 0.2 | No last-used time on keys in 0.2 | It would add a write to every call |
| D39 | 0.2 | The ledger's format version moves to 2 | Records carry attribution; D8 then refuses a 0.1 directory instead of misreading it |
| D40 | 0.2 | A ledger is built in staging and renamed into place; the engine never deletes a directory at a ledger's final name; once the bootstrap is marked the ledger opens only with `open_existing_blocking` | A crash at any point of creation leaves either a deletable staging directory or a complete ledger; a lost, emptied or foreign ledger is refused, never replaced |
| D41 | 0.2 | Opens are bootstrapping, finishing or later; only a bootstrapping open undoes, and only before its rename; the mark is a bootstrapping open's last fallible step | Every failure has one defined outcome. An open that finds an unmarked bootstrap and commits its mark has finished it, revoking the unreturned minted key; if it succeeds, it says so and returns a replacement unless a seed is given. If it does not, no later open says so |
| D42 | 0.2 | A key refused as expired is flagged `expiry_recorded`, and a flagged key stays expired; the flag does not spread to its children; if recording it fails, the call keeps its uniform refusal and a later refusal tries again | A clock stepped back, before or after a restart, does not revive a recorded expiry; a clock that runs ahead expires only the keys refused meanwhile; refusals write at most once per key; no global floor ties key time to event time |
| D43 | 0.2 | Key changes re-check their calling key after taking the write lock, and a refused one writes nothing but a newly expired caller's `expiry_recorded` (D42); an emit admitted before a revoke may commit after it | A revoked or expired key never changes keys; a lock across the ledger would cost every emit |
| D44 | 0.2 | Any control-plane failure is `Unavailable`, retried at once, except a failure to record an expiry (D42); `retryable()` means the unchanged request may succeed later, and `hint` says when (at once, after a revoke, after reopen); the cap is `ResourceExhausted` and counts a created key until it is revoked or its expiry is recorded | The call fails closed without closing the engine; one flag answers "may I retry" and the hint answers "when", so no kind splits on timing; a cap that a clock set back cannot overfill |
| D45 | 0.2 | `Call` carries the raw key as a `Secret`; the engine parses and verifies it on every call, with no cache | Revocation and expiry act on the next call; a digest lookup by ID is cheap; the raw key never sits in a printable type |
| D46 | 0.2 | Keys are `ixk_<key-id>_<secret>`, 84 characters; the control plane stores SHA-256 of the whole text and compares in constant time | A 256-bit random secret needs no slow hash; the ID gives a direct lookup |
| D47 | 0.2 | `control.db`'s format version is 1 in 0.2.0, the first release with that file, whatever its schema was while 0.2 was built. A test pins the schema, and from then on a change to it changes the version too | Only a build from before the release could have made an older file; after it, D8's loud refusal beats a silent misread |
